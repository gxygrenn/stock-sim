## 四、关键发现：服务端结算逻辑缺陷（本次复盘核心）

### 4.1 事实 A：结算日与行情日错配 + 重复结算

服务端 `settle()` 仅在「交易日历 `nextDate <= 今天` 且时间 ≥15:10」时触发，且**每次扫描最多结算 1 天**。日志证据：

```
2026-09-23 21:28:24  自动结算 2026-09-22（大盘 -0.39%）
2026-09-25 20:15:56  自动结算 2026-09-23（大盘 -1.22%）
```

而通过腾讯行情接口核实的**上证指数真实日线**：

| 日期 | 收盘 | 真实涨跌 |
|---|---|---|
| 09-22 | 3952.13 | +0.056% |
| **09-23** | 3936.52 | **-0.395%** |
| **09-24** | 3888.37 | **-1.223%** |

**结论：`history` 表中 `date=2026-09-23, mkt=-1.22%, total=99580.23, dayPnl=-1016.00` 这一行，实际是用 09-24 的收盘价算出的 09-24 结果，却被贴上了 09-23 的日期标签。** 后果：

1. **09-23 被结算两次**——09-23 21:28 与 09-25 20:15 各写一行，`mkt` 分别为 -0.39% 与 -1.22%；
2. **09-24 与 09-25 两天完全没有 history 行**，净值曲线缺失两个交易日；
3. `ret=-0.4198%` 与 `mret=-0.0322%` 的**超额收益归因从此错位**——它比较的是「账户在 09-24 的表现」与「指数在 09-24 的累计表现」，两者本应对齐却被挂到 09-23。

**这是历史累计超额收益（`ret` vs `mret`）不可信的根因。** 当前 `ret=-0.42%` vs `mret=-0.03%`，看似跑输 0.39pp，但该对比的两个数字分属错配的时间点。

### 4.2 事实 B：指数取数失败，用旧缓存掩盖了缺陷

2026-09-25 20:15:56 的 `s["quote"] = null`，说明 `refresh_prices()` 取指数行情**失败**，`settle()` 遂落入 `q.get("pct", 0.0)` 的兜底分支。它没有结算成 0.00%，是因为 `s["quote"]` 保留了**上一次成功缓存的旧 quote**（pct=-1.22）。

这构成了一个隐蔽的失效链：**取数失败 → 用过期缓存 → 恰好给出非零错值，反而掩盖了 4.1 的错配**。若缓存也为空，会静默结算成 0.00%，问题更难发现。

### 4.3 技术面信号长期全量失效

日志每一轮扫描都记录：

```
技术面数据获取失败 5/20 只，本轮该维度记 0 分
技术面获取失败(000778): K线全部源不可用: list indices must be integers or slices, not str
K线源切换 -> ifzq.gtimg.cn
```

四路信号（技术面 / 龙虎榜 / 公告 / 估值）中**技术面这一路长期全量记 0 分**，等于四路实际只有三路在工作，`delta` 分被系统性低估。在 `buySigFloor=0` 的门槛下，这使买入信号更难被跨过——**与 11 日零成交互为因果**。

### 4.4 附带确认的既有修复

`reviewMaxAgeMin=240` 的过期清理工作正常：09-22 的滞留候选在 09-23 已清空，本次 `pendingReview=[]`，09-15 记录的空转覆盖问题**未复发**。

## 六、经验蒸馏（可复用）

1. **结算日与行情日错配会污染净值曲线，使超额收益归因失效** —— 09-23 真实 -0.395% 被记为 -1.22%（贴错标签），09-24 与 09-25 两天零 history 行，同一日被结算两次。**只要该缺陷未修复，任何基于 `history` 的「跑赢/跑输指数 X pp」结论都不可信。** 引用历史数据前必须先核对 `history[-1].date` 与 `history[-1].mkt` 是否与真实指数日线一致。
2. **四路信号长期缺一路（技术面），导致买入门槛系统性偏紧** —— 日志稳定输出「技术面数据获取失败 5/20 只，本轮该维度记 0 分」，`delta` 分被低估，在 `buySigFloor>=0` 下买入更难触发，与 11 日零成交互为因果。评估「门槛是否合理」前必须先把这一路修好，否则是在用残废的四路体系调参。
3. **零成交状态下「持有即决策」，缺省意味着满仓承担 beta** —— 11 个交易日无任何交易，持仓持续暴露，当日 7 只中 4 只下跌、持仓口径 -1.576% 跑输指数约 0.35pp，金融板块 32.98% 集中度贡献了三只全部下跌。**「持仓复核」必须纳入每日必做项**，而非默认不动作。

## 七、参数建议

**建议：不调整任何交易参数，优先修复服务端 `settle()` 的交易日历对齐与单日单次结算逻辑。**

依据：`settle()` 当前「每次扫描最多结算 1 天」+ 依赖可能过期的 `quote` 缓存，直接导致了 §4.1 的 09-23 重复结算与 09-24/09-25 漏结算，进而使 `ret` / `mret` 超额收益归因错位。该问题属**数据完整性缺陷，不是策略参数问题**，抬门槛、改冷却时间、调 `buyPct` 均无法解决。
