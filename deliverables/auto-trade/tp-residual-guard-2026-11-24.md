# 止盈残仓保护 · 参数方案与回测（2026-11-24）

## 一句话结论

「8% 止盈卖一半、残仓跌回卖价 −1.5% 即清」在 12 个历史 episode 上带来 **+1,998 元**（基准 +8,787 元，改善 22.7%），
但其中 **91% 来自两笔**（莫德纳 +1,184、中国电信 +527），其余 10 笔合计仅 **+287 元** —— 这是廉价保险，不是 alpha。
同期「8% 直接全清」改善 **+2,728 元**，略优于保护线，但样本只覆盖一个回落区间，上行区间的机会成本无法估计。

**真正该先修的其实是另一件事**：建设银行 11-20 收盘浮盈 +8.75%（盘中最高 +8.92%），一分没卖 ——
不是参数问题，是扫描时点盲区（14:40 之后才拉过 8% 线，下一次检查已经是次日）。

---

## 一、规则定义（三档方案，互斥，别叠加）

| 方案 | 规则 | 需要改哪里 | 性质 |
|---|---|---|---|
| **A 残仓保护**（推荐备选） | 触发 `takeProfitPct=8` 卖出 50% 后，剩余仓位记录卖价 S；此后任一交易日**盘中价 ≤ S×(1−1.5%)** → 以触发价清掉残仓。每 episode 只触发一次 | `check_stops()` 增加字段 `residualGuardPct`，持仓对象加 `tpSellPrice` | 服务端代码 + 新参数 |
| **B 8% 全清** | `takeProfitPct` 命中后卖 100%，不再保留半仓 | 改 `check_stops()` 的 `sellPct` 语义（现为 0.5） | 服务端代码 |
| **C 收盘前补扫**（与 A/B 无关，可独立上） | 14:55 增加一次纯代码 `check_stops`（不调 LLM，不发评审） | 调度 + `sim_engine` 增加轻量入口 | 服务端调度 |

参数建议（若选 A）：

```
residualGuardPct = 1.5        # 残仓保护线，相对止盈卖价
residualGuardOnce = true      # 每持仓只触发一次，清仓后重置
```

判定细节：
- 卖价 S 取**实际成交价**（不是当日收盘），因为盘中止盈可能高于收盘。
- 触发用盘中最新价（与 `check_stops` 现有口径一致），成交按触发价，跳空低开按开盘价。
- 与 `trailPct` 的优先级：保护线在前（更紧），命中即清，不再走 trail。
- 与 `loseCutPct` 的关系：us 已开 −2% 减半，残仓若已减半则保护线只作用于剩余部分，不冲突。
- 回滚：`residualGuardPct=0` 即关闭，等价现状。

## 二、回测方法与口径

- **样本**：三账户 live state 全部历史 trades（截至 2026-11-24 11:20），按 code 聚合连续持仓 episode，只保留**收盘浮盈曾 ≥ +8%** 的 12 个（A股 9 + 美股 3）。
- **数据**：腾讯日K（`server.fetch_kline`），窗口 = 首笔买入日 ~ 清仓日（未清仓截至 11-24）。
- **触发日**：收盘浮盈首次 ≥ 8% 的交易日，卖价取当日收盘（保守，实盘多卖在盘中更高价）。
- **基准臂**：止盈卖 50%，残仓只靠 `trailPct`（要求仍浮盈）与硬止损（A股 −6/−8，美股 −6）。
- **对照臂**：基准 + 残仓保护线，档位 1.0 / 1.5 / 2.0 / 2.5 / 3.0%；另跑「8% 全清」臂。
- **成交约定**（关键，避免口径漂移）：保护线与硬止损统一按「盘中最低触及、成交价 = min(开盘价, 触发价)」；trail 按收盘。全部无未来函数。
- 第一版曾把保护线按收盘价成交、硬止损按触发价成交，两个口径混用导致莫德纳被算成 −285 元（假象）；统一后重跑，结论才稳定。

## 四、稳健性检查（必须看的三个否决点）

1. **收益极度集中**：1.5% 档的 +1,998 里，莫德纳 1,184 + 中国电信 527 = 1,711（85.6%）。剔除这两笔，10 个 episode 合计 **+287 元**（人均 +29 元，约等于噪声）。全清档剔除这两笔后 +676 元。
2. **样本期偏差**：12 个 episode 全落在 10-14 ~ 11-24，是一个「11 月初冲高、随后回落」的单边区间。保护线在回落市天然占优，**上行区间会被反复打脸**（1% 的保护线在 A 股等于日常波动幅度，几乎每次回调都会触发）。
3. **噪声触发率**：1.0% 档触发 8/12，说明残仓基本在止盈后 1~2 天内就被清掉 —— 实质上把「卖一半」退化成了「卖 100% 但晚一天、价格差 1%」。这也解释了为什么 1.0% 档（+2,179）已经逼近全清（+2,728）。
4. 反例成本很小：1.5% 档唯二恶化是伊利 −20、农行 −50（合计 −70），远小于收益。

**结论**：如果目标是「锁住 8% 附近的利润」，**B（全清）比 A 更彻底且更简单**；如果要保留上涨弹性，A 的 1.5% 档是折中。两者都不该被当作「提高胜率」的手段 —— 它只是把右尾削掉。

## 五、另一个更值得先修的问题：扫描时点盲区

建设银行 11-20 日K：开 12.34 / 高 12.78 / 收 12.76 / 低 12.34，成本 11.733，8% 线 = 12.672。
- 收盘浮盈 +8.75%，盘中最高 +8.92%，**全天已越过 8% 线**；
- 但 `tpDate` 为空、11-20 无任何卖出，残仓 1,288 股一路到 11-24 的 12.37，峰值回吐 −374 元；
- 11-23 盘中又到 12.72（+8.41%），收盘回落到 12.39，同样没触发。

现有的 `check_stops` 只在扫描时刻取价：A 股每小时 :40（9:40 / 10:40 / 13:40 / 14:40）。
14:40 之后到 15:00 收盘是**20 分钟盲区**，开盘 9:30~9:40 也有 10 分钟盲区。建行 11-20 的 8% 极可能落在 14:40 之后。
这类「根本没机会触发」的漏卖，比参数调优更值得先修 —— 而且不需要动任何交易参数。

**推荐动作（方案 C）**：14:55 加一次纯代码 `check_stops`（不调 LLM、不发评审、不产生 token），成本接近零，可覆盖收盘前拉高。
同日 A 股 14:55 的这次检查若触发止盈，成交价仍在集合竞价前，可正常成交。

**落地备注**：本轮 P1 与 B 同时上线，两者不冲突（P1 是「多看一眼」，B 是「看的时候卖多少」）。
P1 最终实现为「请求触发为主」：14:40–14:59 内任何一次 API 访问都会触发一次 `check_stops`（3 分钟节流、可重复查），
因为云端沙箱无人访问时后台线程会被挂起——首版只挂在 worker 循环里，实测 80 分钟未执行。
A 档未采用，但回测脚本 `_residual_sim.py` 保留，若日后想换回「留半仓 + 残仓保护」，

## 七、不可验证 / 未做

- 建行 11-20 的具体触发时刻需要分钟级数据，日K无法确认「14:40 时价格是否已在 12.67 以上」；结论基于「收盘与盘中最高都远高于 8% 线、且当日无任何卖出」推断。
- 回测未覆盖 2026-10-14 之前已清仓的 episode（state 只保留近期 trades），样本量偏小。
- 未模拟「保护线 + trail 同时存在时的路径依赖」（比如保护线触发后当日又被 trail 覆盖的情形），因为两者优先级已定为保护线优先。
- 未评估 A 方案与 us 现有 `loseCutPct=-2 / trailArmPct=4` 的交互，us 侧建议先在纸上跑通再上。
